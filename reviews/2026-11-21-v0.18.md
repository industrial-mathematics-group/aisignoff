# AI review of aisignoff 0.18.0

- **Reviewer:** Claude Opus 5.5 (Anthropic), new session without the generating conversation. The repository names Claude Opus 5.5 in `Assisted-by`, so this is a review by the same model: **A1**, although it brings new evidence.
- **Reviewed:** `main` at `b4199c9` (0.18.0), on 2026-11-21. The focus is what changed since 0.15.0: the findings axis and A1 findings, `aisignoff guide`, review pull requests and record files in `reviews/`, attestations of a commit, the removal of freeze and snapshots, the blame cache, the split between `SIGNOFF.toml` and `reviews/`, and `gc` with dead records.
- **Level:** A1
- **Highest finding in this change:** major

## Summary

The new release mostly holds up. The test suite passes, and the blame cache gave the same results as plain `git blame` in every comparison I ran (details under New evidence). The problems are in how reviews are ordered and in what the check before the merge protects. In two common cases a critical finding disappears or can't be cleared:

- An attestation of a commit always counts as the newest review, so it overrides a whole-file review that was recorded later.
- `SIGNOFF.toml` always counts before `reviews/`, so a re-review recorded with `--signoff` (as the signoff request and `@signoff` workflows record it) can't replace a finding that is in `reviews/`.

Separately, `[review] dir` is not a protected setting. A pull request can use it as an `exclude` that the check doesn't catch, or to get around the add-only rule.

## Findings in this change

| # | Severity | Where | Finding |
|---|---|---|---|
| 1 | major | `src/aisignoff/history.py:985`, `:1412` | **An attestation of a commit always counts as the newest review.** `_scoped` gives it the content age `newest`, and `_line_pieces` orders reviews by content age before the order they were recorded in. Suppose commit X is reviewed (`--commit X`, findings `none`), and later the whole file is reviewed (blob of the current file, findings `critical`). As soon as any other line of the file changes, the whole-file review's content is no longer the newest, and X's lines show `none` again, although the critical review was recorded later and saw those same lines. This breaks "the later review counts" (history.md) and "the later review of the same lines gives their findings" (signoff-toml.md). The review guide recommends both kinds (`--commit` for a diff, a path for a whole file), so mixing them is normal. Repro: `review_order.py`. |
| 2 | major | `src/aisignoff/history.py:916`; `examples/workflows/signoff-request.yml:288`, `signoff-assistant.yml:423` | **A re-review recorded with `--signoff` can't clear a finding that is in `reviews/`.** Every attestation in `SIGNOFF.toml` counts before every record file, whatever their dates (as documented). 0.18 has the signoff request and `@signoff` assistant workflows record AI reviews with `attest --signoff`, into `SIGNOFF.toml`. So when a review pull request records a critical finding and a re-review of the fix and the original commit later goes through the signoff request, the original commit's remaining lines keep the critical finding forever. The fix commit's lines show `none`. Only a new record file in `reviews/` clears it. Repro: `signoff_first.py` (with the record-file control). |
| 3 | major | `src/aisignoff/pullrequest.py:117-160`; `src/aisignoff/config.py:311` | **`[review] dir` is not a protected setting in the check before the merge.** `base_rules` protects `[policy]`, `exclude`, `[history]`, `version` and the ignore-revs file, but not `[review]`. That exemption made sense while `[review]` only held `recheck` (rc9). Since 0.16, `dir` decides which files need no declaration and which files are add-only, and the check uses HEAD's value. (a) A pull request that sets `dir = "src"` passes, and `src/` is no longer declared or reported. The same change written as `exclude = ["src/**"]` is refused. (b) A pull request that sets `dir = "reviews2"` can rewrite an earlier review in `reviews/` in the same change and pass, which defeats add-only. A code owner on `SIGNOFF.toml` (signoff-toml.md) mitigates this, but the check exists so that it doesn't depend on that. Repro: `review_dir.py`. |
| 4 | minor | `src/aisignoff/history.py:1033-1039` | **The report named by a record file (A2/A3) can be any existing file.** `_review_record` calls `review_problems` without the change's files, so the rc8 rule ("the report must be a file the pull request adds or modifies, or a link") applies to pull request descriptions only. A review-only pull request can attest A3, findings `none`, and name an earlier review's report or `README.md`. It passes, and needs no declaration. The same claim in a description is refused. Repro: `record_report.py`. |
| 5 | minor | `src/aisignoff/cli.py:314-367` | **A code pull request can add a record file that raises its own lines.** A description that declares A0 together with a `reviews/x.toml` that attests the changed file's new blob at A3, findings `none`, passes the check without a note. After the merge, the lines show A3/F0. The dev guide forbids this, but the check doesn't flag it, even though a pull request that both changes content and adds a review record is easy to detect. A related case, by design ("the newest review counts, not the highest level"): an A1 record by the author's own model can replace an earlier A2/A3 finding of `critical` with `none` in a review-only pull request that needs no declaration. Repro: `review_folder_misc.py` (second part). |
| 6 | minor | `src/aisignoff/history.py:919` | **AI reviews in `SIGNOFF.toml` aren't checked like those in `reviews/`.** An `[[attestations]]` entry in `SIGNOFF.toml` with `AI-Review = "A3"`, no `AI-Review-Findings` and a report that doesn't exist passes `lint`. The same entry in `reviews/x.toml` fails twice. `attest --signoff` refuses it, but a hand-edited entry (or a `[[commits]]` entry from `correct -a A2`) gets through. This repository's own `SIGNOFF.toml` has three such A2 entries from before findings existed, so 849 lines show A2 with F-. That is allowed for a review older than findings, but `lint` can't tell such an entry from a new one. Repro: `signoff_attestation.py`. |
| 7 | minor | `src/aisignoff/config.py:218` | **Every `*.toml` under the review folder is read as a record file.** A3 evidence that includes a TOML file (the `pyproject.toml` of a small test project, a config) makes `lint` and `report` stop with exit 2 for the whole repository. The add-only rule then forbids removing the file in a later change. The review guide tells A3 reviewers to commit their evidence into this folder. Repro: `review_folder_misc.py` (first part). |
| 8 | minor | `src/aisignoff/history.py:993-1022` | **`gc` deletes records of excluded files.** `dead_records` only sees the origins of the files it resolved, and excluded files are never resolved. So a person's attestation of a file under `exclude` is reported as covering no line, and `gc` deletes it. If the exclusion is lifted later, the file has lost its review. That contradicts "their levels are unchanged" once the exclusion changes. Repro: `gc_excluded.py`. |
| 9 | trivial | `src/aisignoff/pullrequest.py:263`; `src/aisignoff/guides/review.md:17`, `dev.md:33` | **Two wordings don't match the behaviour.** For a record file that has landed, plain `lint` says "the review report … isn't in this change: commit it with the pull request", even when no pull request is involved. And both guides say "`lint` fails a change that edits" the review folder, but only the check before the merge (`--declare-from`/`--base`) does. |

## New evidence

This is not A3, since the reviewer is the same model. The evidence is still useful for the next A2/A3 review:

- **Blame cache, compared line by line** (`cache_rows.py`). Walk the first-parent history, warm the cache at each sampled commit, and compare `History._base_blame` against a plain `git blame` of the whole history, for both the first-parent blame and the blame of the commits that wrote each line. On this repository (74 first-parent commits, every 10th, up to 40 files each) 290 files matched. On pallets/click (1392 first-parent commits, 1226 merges, every 100th, 40 random text files each) 560 files matched. 0 differences.
- **Blame cache, compared by results** (`cache_diff.py`). `report --json` with the warmed cache against `AISIGNOFF_NO_CACHE=1`, at 10 commits of this repository and 12 of click. All identical.
