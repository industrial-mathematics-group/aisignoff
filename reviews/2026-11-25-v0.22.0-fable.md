## Summary

0.21.0 and 0.22.0 hold up in the main use case. The test suite and `lint --strict` pass, no probe produced a crash or a wrong level in a plain repository, and the central promise of 0.22.0 survived a differential test: in 300 random cases the levels of every line were the same before the merge, after it, and with the blame cache on. No way was found to get an invalid declaration through `lint`.

What remains are six minor findings at the edges of the two changes. Three are behaviour (files that git converts are still one unit before the merge; `diff` miscounts a replaced binary file without line parts; a pull request can't remove an unknown key from the default branch's `SIGNOFF.toml`), and three are places where the draft contract promises more than the code does (git configuration that still changes levels before the merge, a rule for template boxes that the code doesn't have, and the git version check that isn't made "at start"). None of them is in the way of using 0.22.0; findings 4 to 6 should be settled, in the code or in the text, before the contract loses its "Draft" box.

## Findings in this change

### 1. Minor — A file that git converts is still one unit before the merge

[`src/aisignoff/history.py:1615`](../src/aisignoff/history.py#L1615), [`src/aisignoff/diff.py:278`](../src/aisignoff/diff.py#L278), missing test in [`tests/test_v021.py:176`](../tests/test_v021.py#L176)

0.21.0 reads a file with `working-tree-encoding` or a filter "as git stores it", but only when the file is as on the default branch. A file that the change under check edits, adds or renames is read from the work tree, where UTF-16 text has NUL bytes and a filtered file is the real binary. So the check before the merge shows such a file as one unit that belongs to the change, and after the merge its lines follow `git blame`:

- A UTF-16 file of four lines, one line edited: before the merge `['H3']` (one unit, the change's); after the merge `['H1', 'H3', 'H1', 'H1']`.
- A new UTF-16 file of three lines: one unit before the merge, three lines after it.
- A file behind a clean filter (a stand-in for Git LFS, three pointer lines in git): one unit before the merge, `['H1', 'H3', 'H3']` after it.
- A UTF-16 file that the change only renames: one unit of its old owner before the merge, four lines after it (the same levels, other counts).

`diff` reads the new side from the blob and counts lines (+1 −1 for the edit), so `diff` and `report` disagree about the same change. This contradicts contract 5.6 ("as git stores it") and 5.7, and the sentence of `docs/history.md` that the check before the merge shows what lands. In v0.20.1 both sides were one unit, wrong but the same. The test added in 0.21.0 checks the landed levels and the counts of `diff`, not the levels before the merge. Evidence: `probe_units.py`, U2 to U4.

### 2. Minor — `diff` counts the lines of a replaced binary file when the old side has no line parts

[`src/aisignoff/diff.py:430`](../src/aisignoff/diff.py#L430), text in [`docs/history.md:330`](../docs/history.md#L330) and [`docs/changelog.md:11`](../docs/changelog.md#L11)

0.22.0 takes git's text diff for a text file that replaces a binary one, and then folds the removed lines into one unit, but only when the old file was resolved line by line. Without `[history]`, or for a file under `precedence = "override"`, each line that git's text diff removes from the binary content is counted: a binary file with three such lines gives `+1 −3` where the docs say "counts the binary version as one removed unit" and where `[history]` gives `+1 −1`. v0.20.1 gave `−1` in all three modes, so this is a regression of the counts (no level is affected). The folder report has it with `[history]` too: `report --html --since main` shows `+1 −3` for the file where `diff main` shows `+1 −1`. `tests/test_v022.py` covers `diff` with `[history]` only. Evidence: `probe_units.py`, U1 and U5.

### 3. Minor — A pull request can't remove an unknown key that the default branch has

[`src/aisignoff/pullrequest.py:126`](../src/aisignoff/pullrequest.py#L126), [`src/aisignoff/cli.py:251`](../src/aisignoff/cli.py#L251), [`src/aisignoff/config.py:337`](../src/aisignoff/config.py#L337)

Up to 0.21.0 an unknown key at the top level, in `[history]` or in `[review]` was a warning, so plain `lint` passed with it. With 0.22.0 the file is refused, which is the decision D2. But the check before the merge (`lint --base … --declare-from …`) also loads the `SIGNOFF.toml` of the base branch for its rules, and stops with exit code 2 when that one has such a key: `SIGNOFF.toml on main: unknown key(s) notes`. The pull request that removes the key therefore fails the check it is meant to fix, and so does one that raises the pin and removes the key together. The ways around are to remove the key while the workflows still pin 0.21.0 or older, or to push to the default branch directly; the changelog entry for 0.22.0 names neither. (`diff` handles the same situation with a note and goes on.) Evidence: `probe_keys.py`, K4.

### 4. Minor — The machine's git configuration can still change the levels before the merge

[`src/aisignoff/diff.py:195`](../src/aisignoff/diff.py#L195), [`src/aisignoff/history.py:59`](../src/aisignoff/history.py#L59), promise in [`docs/contract.md:29`](../docs/contract.md#L29) and [`docs/compatibility.md:12`](../docs/compatibility.md#L12)

Contract 2.2 says that a result doesn't depend on the user's or the system's git configuration, and marks that as done in 0.21.0. Two inputs still get through to the diff against the default branch, whose hunk headers aisignoff reads as "these lines changed":

- `diff.interHunkContext = 10` in the user's configuration joins nearby hunks. With three one-line edits in a file of 20 lines, lines 5 to 15 all become the change's (H3) instead of lines 5, 8 and 15.
- `GIT_DIFF_OPTS=--unified=3` in the environment overrides `--unified=0`, with the same effect on every changed file. Contract 2.1 and section 8 name the environment variables that are inputs, and this isn't one.

Only lines that haven't landed are affected (`lint` and `report` with `--declare-from`, `diff`); after the merge all 33 settings and variables tried give the same result. The behaviour is the same in v0.20.1; it is listed here because 0.21.0 is the release that closes this gap by its own account, and the contract and `compatibility.md` now say so. Evidence: `probe_gitconfig.py`.

### 5. Minor — The contract has a rule for human review boxes that the code doesn't have

[`docs/contract.md:89`](../docs/contract.md#L89), [`docs/history.md:178`](../docs/history.md#L178), code in [`src/aisignoff/history.py:428`](../src/aisignoff/history.py#L428)

The grammar written down in 0.21.0 says: "A ticked box above an unticked one is an error." The code takes the highest ticked box and reports nothing: a description with H2 ticked and H0 and H1 unticked passes `lint --declare-from` as H2. That is also what the changelog says (the error was removed after 1.0.0rc6), what `docs/history.md` says earlier on the same page ("ticking the ones below as well changes nothing"), and what the organisation's template asks for ("tick the highest one you did"); pull requests #68 and #69 are declared that way. The sentence is wrong in both normative places, and under contract section 3 a text like this decides later what counts as a bug. Evidence: `probe_grammar.py`, G1.

### 6. Minor — git's version is checked only where history is read

[`src/aisignoff/history.py:529`](../src/aisignoff/history.py#L529), [`src/aisignoff/diff.py:308`](../src/aisignoff/diff.py#L308), promise in [`docs/contract.md:30`](../docs/contract.md#L30)

Contract 2.3 says that aisignoff "checks the version at start and stops with exit code 2 below it", and 6.2 lists a git that is too old under exit code 2 for every command. The check is made when the history is built and in `diff`. With git 2.30, `lint`, `report` and `badge` in a repository without `[history]` run and exit with 0, and so do `attest` and `correct` with `[history]` on. The results of those runs are right, since they need nothing newer from git; it is the promise that is wider than the code. Evidence: `probe_exit.py`, X1.

### 7. Trivial — Texts that are out of date or don't match

- [`docs/contract.md:4`](../docs/contract.md#L4) says "aisignoff is at 0.20.1"; [`docs/contract.md:173`](../docs/contract.md#L173) still says that the CI change waits in the description of #68, while `ci.yml` has it.
- [`docs/report.md:183`](../docs/report.md#L183): "its result is its exit code (0, 1 or 2)", without 3.
- [`src/aisignoff/config.py:154`](../src/aisignoff/config.py#L154): the comment says that unknown keys are warnings; the `warnings` parameter of `_parse_history` ([line 487](../src/aisignoff/config.py#L487)) is no longer used.
- Contract 4.2.3 says that the error for an unknown key "says it is a typo or a key of a newer aisignoff, wherever it is". In `[policy]` ([`model.py:178`](../src/aisignoff/model.py#L178), [183](../src/aisignoff/model.py#L183)) and at the top level of a record file ([`config.py:263`](../src/aisignoff/config.py#L263)) the message doesn't say so (the exit code is 2 everywhere).
- The grammar gives a key line the form `Key: value`; `Key:value` without the space is read too ([`history.py:224`](../src/aisignoff/history.py#L224)).

## Outside this change

### 8. Minor — `guide --agents-md` and `init` end with an internal error on an `AGENTS.md` that isn't UTF-8

[`src/aisignoff/guide.py:120`](../src/aisignoff/guide.py#L120)

Both exit with 3 and a traceback; `init` has written `SIGNOFF.toml` by then. By contract 6.2 a file that can't be read is exit code 2. The code is unchanged since before v0.20.1, where the same run printed the traceback and exited with 1; 0.21.0 only changed the code it exits with. Evidence: `probe_exit.py`, X4 and X6.

### 9. Minor — `lint` passes when git can't read `HEAD`

[`src/aisignoff/history.py:547`](../src/aisignoff/history.py#L547)

With a corrupt commit object at `HEAD`, `lint` and `report` treat the repository as one without commits: every line counts as not landed, nothing fails, and `lint` exits with 0 and "All files are declared". Contract 6.2 puts "a git that … fails" under exit code 2. A far edge, and unchanged: v0.20.1 does the same. Evidence: `probe_exit.py`, X5.

### 10. Trivial — With `ignore-whitespace`, `diff` counts lines as added that keep their owner

[`src/aisignoff/diff.py:401`](../src/aisignoff/diff.py#L401)

`diff` compares without `-w`, while the levels are resolved with it. A line that changed only in whitespace is counted as added, with the levels of the commit that keeps owning it (99 of the 300 fuzz cases). That can be read as intended, since the line did change; it is noted because the count of added lines is then not the count of lines the change will own. The line is unchanged since before v0.20.1.
