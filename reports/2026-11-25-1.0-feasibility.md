# aisignoff 1.0: feasibility report

*25 November 2026, on `main` at `610ca2b` (aisignoff 0.20.1). Written with the draft [1.0 contract](../docs/contract.md), which says what 1.0 would promise; this report says how far 0.20.1 is from it.*

## Verdict

**1.0 is feasible, but not yet.** The design has settled, the tests and the tool's own declarations are in order, and every repository that uses it already runs 0.20.1 on `SIGNOFF.toml` version 4. Releasing it as 1.0 today would still promise things that are false:

- a traceback exits with the code that means "declarations invalid";
- the user's git config and replace refs can change the levels of lines;
- one known defect gives lines wrong levels after a binary file becomes text;
- the declaration grammar and several resolution rules are written down only in the code, so "a fix that contradicts the docs" can't be told from a breaking change.

Each of these is small to fix: about a week of work, almost all of it independent pieces. The real constraint is time. The format last changed in a breaking way on 21 November (0.19.0), four days ago. Each new review has found something, two of the last five fix releases introduced a new finding, and the last attempt at 1.0 (1.0.0rc1 to rc10) went back to 0.x because the format kept changing.

**Recommendation:**

1. Do the work packages below as 0.21.0.
2. Get one more independent whole-codebase review of 0.21.
3. Release **1.0.0 directly**, with no new release candidates, when all of these hold:
    - every [Before 1.0 item](../docs/contract.md) of the contract is done;
    - a whole-codebase review of the release finds nothing major or critical;
    - at least two weeks have passed with no **Breaking** or level-changing entry in the changelog.

### What the reviews found

| Date | Review | Highest |

Every finding in the committed reports has a fix with a regression test (`tests/test_review_*.py`, 114 tests), except the open ones below. The reviews of 0.7–0.14, of rc7 and rc9, and of 0.19.0 that the changelog mentions aren't in `reviews/`. `visualize.py`, `config.py`, `model.py`, `pullrequest.py`, `cache.py`, `project.py` and `guide.py` were only reviewed as part of the whole codebase, and nothing has reviewed 0.20.1 as a whole.

The findings cluster in four places, and these are the design risks:

- **Binary or text.** aisignoff has its own probe (a NUL byte in 16 KiB) next to git's (8,000 bytes), and has to correct git's patches for `-diff`, `binary`, `textconv`, `working-tree-encoding` and filters. This produced six findings, and each fix has opened another case. *Option:* compute both sides with aisignoff's probe from the blobs and never use git's text/binary decision. 0.20.1 moved most of the way there.
- **Which review counts.** The order of reviews was redefined in rc10, 0.19.0 and 0.19.1. That is the rule users least expect to change, and the one the contract freezes.
- **The cache and `gc`.** `gc` and the "which entries have landed" check edit and read `SIGNOFF.toml` line by line next to the TOML parser. That caused the one critical finding; it fails safe now.
- **English text heuristics.** The old-template A1 box (`its own work`, `self-check`), self-check and negation words, and model names compared by their words make the template grammar depend on wording, not markup.

### Process

- **"Outside this change" findings need a home.** The defect above was known, fixed halfway, and is invisible in the findings axis. A review that finds a problem outside the change should lead to an issue (or a record on the file); otherwise the F0 of the report claims more than the reviews found.
- **Missing reviews.** About ten reviews that the changelog mentions aren't in `reviews/`. That doesn't block 1.0, but the review history is part of what the tool asks of others.
- **Human review.** No line of `src/` is above H1. For a tool whose purpose is honest review levels, a person's line-by-line review (H2) of at least `history.py`'s resolution rules and `model.py`'s checks would make 1.0 more credible. That is the maintainers' call, not a technical gate.
- **The v0.20.0 tag** points at a web-UI commit titled "Update print statement from 'Hello' to 'Goodbye'" that re-adds `highlight.min.js`. That is harmless, but confusing in a release history.

## Work packages for 0.21

Effort is agent working time plus a person's review; the packages are independent except where noted.

1. **Git isolation** (½ day): pin `diff.indentHeuristic=true`; add `--no-textconv` to blame; set `GIT_NO_REPLACE_OBJECTS=1` (consider `GIT_CONFIG_NOSYSTEM=1` and `diff.renameLimit`); require git ≥ 2.31 at start; put the git version in the cache key. Each is a **Levels** fix for the repositories affected; tests with a scratch repository per setting.
2. **Exit codes** (½ day): catch `OSError`, `UnicodeDecodeError` and unexpected exceptions in `main` → message and exit `2` (or `3`, [D3](../docs/contract.md#decisions)); turn the three "names nothing" history problems into configuration errors for every command.
3. **Forward compatibility** (½ day): per [D2](../docs/contract.md#decisions), either unknown keys warn in every table and in record files, or the docs say they never get new keys; the "newer aisignoff" message for `version > 4`.
4. **Binary-to-text after landing** (1–2 days): make landed history follow the same unit rule as `diff` (a text side that replaces a binary one is all new), with the rule in the docs; a **Levels** fix. Fix the encoding/filter miscount in `diff` with the same shared probe (read both sides from blobs, or both from the converted content).
5. **Normative docs** (1–2 days, after 4): move the grammar of §4.3 and the code-only resolution rules into `docs/history.md`; fix the JSON reference, the command reference (four badges, `correct`/`gc` in the table, `init`), the shallow-clone contradiction and the exit-code wording; replace "What 1.x will keep stable" in `compatibility.md` by a summary of and a link to the contract.
6. **CI** (¼ day): Python 3.14; a job with the lowest supported git (a container image with git 2.31), so the minimum is tested, not only stated.
7. **Review and soak** (2+ weeks, after 1–6): a whole-codebase independent review of 0.21; fixes; no **Breaking** or **Levels** entry for two weeks; then 1.0.0 with the contract's "Draft" box removed.

## Decisions for the maintainers

The contract lists them with the option it assumes:

- **D1:** when to release (assumed: after the work packages and a soak);
- **D2:** unknown keys in tables (assumed: warn everywhere);
- **D3:** one error code `2` or a separate `3` for unexpected errors (assumed: `2`);
- **D4:** Linux only, or macOS too (assumed: Linux);
- **D5:** git versions outside the line-stability promise (assumed: yes).

## Update: decisions and fixes (25 November 2026)

The maintainers decided D1 (wait with 1.0.0), D3 (a separate exit code `3`), D4 (Linux only, for containers) and D5 (keep git). D2 (keys) and a new D6 (a text file after a binary one) are open. See [Decisions](../docs/contract.md#decisions) in the contract.

Pull request #68 (0.21.0) does work packages 1–3 and 5, and the notes: exit codes `2`/`3`, settings that name nothing as configuration errors, the git isolation with a minimum of git 2.34 (Ubuntu 22.04's, instead of 2.31), files that git converts read as git stores them (the `working-tree-encoding` minor), the shebang, `guide --skills`, the badge encoding, the `init` suggestion, and the docs. Still open:

- work package 4 (binary to text), which waits for D6;
- the D2 part of package 3;
- package 6 (CI), whose workflow change is in the description of #68, since the GitHub App can't push workflow files;
- package 7 (review and soak).

## How this report was made

Claude Opus 5.5 read the code, docs, changelog and reviews, ran the tests and `lint`, and had three subagents audit, read-only, the compatibility promises against the code, the review history, and the stability of line levels (with probe repositories under `/tmp`, not committed). Of the findings marked B, the traceback exit code and the binary-to-text defect were reproduced again by hand before writing; the three git settings rest on the subagent's probes. No code was changed.
